# ct-log-attack-surface-mapper

Attack surface mapping built from **Certificate Transparency logs**: groups infrastructure by shared IP, flags historical hostnames with no active DNS, and suggests unseen candidates based on real naming patterns. Fully passive reconnaissance.

---

## Motivation

Querying `crt.sh` to list a domain's subdomains is a standard recon step, and tools already do this well (`crt.sh` directly, `ctfr`, `amass` plugins). The result usually stops there: a flat list of names.

That listing, however, holds more information than is typically used:

- **Historical certificates, not just currently valid ones.** A name that once had a certificate but doesn't anymore may still have active DNS and a live service behind it — exactly the kind of asset an internal inventory tends to miss.
- **IP reuse.** Two names with no obvious relation to each other may share the same host or load balancer, revealing infrastructure blocks that aren't visible from the names alone.
- **An organization's own naming convention.** If `dev-` and `staging-` prefixes show up, it's reasonable to suspect a `prod-` equivalent exists (or existed), even if it never appeared in a certificate.

This project combines all three signals into a single passive pipeline.

## How it works

```
 domain
   │
   ▼
 crt.sh ────────► historical certificates (%.domain.com)
   │
   ▼
 SAN extraction ► unique names, normalized, wildcards resolved to their base
   │
   ▼
 DNS resolution ► IP for each name (or no resolution at all)
   │
   ▼
 Grouping ──────► names grouped by shared IP
   │
   ▼
 Patterns ──────► frequent prefixes/suffixes + suggested candidates
```

1. **crt.sh query.** `%.domain.com` is queried in JSON format, which includes historical certificates, not just currently valid ones.
2. **Name extraction.** Each entry can list several SANs separated by newlines. Names are lowercased, and wildcards (`*.domain.com`) also contribute their base form.
3. **DNS resolution.** Each name is resolved with `socket.gethostbyname`. Names that don't resolve are flagged as historical candidates, without assuming they're fully decommissioned (they could still resolve on internal DNS).
4. **IP grouping.** Names that do resolve are grouped by IP and sorted by group size, since IPs with more shared names tend to be the infrastructure worth reviewing first.
5. **Pattern detection.** Prefixes and suffixes appearing 2 or more times across observed names are identified, and candidates are generated by combining those tokens with already-seen base names — **not** by brute-forcing a generic wordlist.

## Requirements

- Python 3.10 or higher
- Internet access, both to `crt.sh` and for standard DNS resolution
- No external tool dependencies (Nmap, Nuclei, etc.)

## Installation

```bash
git clone https://github.com/diegoreija/ct-log-attack-surface-mapper.git
cd ct-log-attack-surface-mapper
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

## Usage

```bash
python3 src/main.py --domain <domain> [--show-unresolved]
```

| Option | Description |
|---|---|
| `--domain` | Root domain to analyze. Required |
| `--show-unresolved` | Also shows names that appeared in certificates but don't currently resolve |

```bash
python3 src/main.py --domain hackerone.com --show-unresolved
```

See [`examples/sample_run.md`](examples/sample_run.md) for a full annotated run.

## Design decisions

- **Historical certificates, not just current ones.** This is the main difference from tools that only show `crt.sh`'s current state.
- **Candidates derived from real patterns, not a generic wordlist.** Environment tokens (`dev`, `staging`, `prod`...) are only used to generate suggestions if they already appear in the observed names for that specific domain. This keeps noise down and stays passive: no full wordlist gets resolved against DNS, only combinations backed by the domain's own data.
- **Stage separation via dataclasses** (`CertEntry`, `ResolvedName`, `IPGroup`, `NamingInsight`), so grouping and pattern logic can be tested without network access.
- **Retries with backoff on the crt.sh query**, since the service offers no availability SLA and can return transient errors.

## Limitations

- Depends on `crt.sh` availability; there's no local cache if the service doesn't respond.
- DNS resolution uses the system resolver; it doesn't distinguish public DNS from split-horizon/internal DNS.
- A name with "no active resolution" doesn't mean the service is fully decommissioned: it may only resolve on an internal network, or the record may have moved to a different DNS provider.
- Candidate generation is limited to combining a single environment token with the base name; it doesn't cover more complex patterns (numbering, regions, dates).
- No verification of revoked certificates or specific transparency logs; it relies on the aggregate `crt.sh` exposes.

## Responsible use

The pipeline is purely passive: it queries a public record (Certificate Transparency) and performs standard DNS resolution, without sending any direct traffic to the discovered services. Even so, use the results responsibly and only as a reconnaissance phase within an authorized engagement.
